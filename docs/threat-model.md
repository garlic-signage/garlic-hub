# garlic-hub Threat Model

This document describes which security properties garlic-hub is designed to
provide, which behaviours are deliberate design decisions, and which risks are
accepted. It exists so that design decisions arising from the constraints of the
digital signage deployment model are not mistaken for implementation defects.

Please read this document before filing a security report.

---

## 1. Deployment Model and Its Constraints

garlic-hub serves content to unattended display devices. These devices share a
set of properties that constrain what authentication mechanisms are available:

- They have no keyboard, no screen for interactive input, and in most cases no
  local UI beyond a setup screen reachable over the network.
- They are provisioned in the field by an installer whose only configuration
  input is a content URL.
- Their firmware is supplied by the hardware vendor. The server operator cannot
  change it, and a vendor firmware update cannot be relied on: the installed
  base includes devices that will never receive one, and any protocol change
  would have to be adopted by multiple independent vendors before it could be
  required.
- They poll the server on a fixed interval and are expected to recover
  unattended after power loss or network outage.

Any authentication scheme that requires the device to present a credential the
server issued through a separate channel is not implementable on third-party
hardware. This is the single most important constraint in this document, and
most of the accepted risks below follow from it.

---

## 2. Assets

| Asset | Description |
| --- | --- |
| Account credentials | Login data for the administrative interface |
| Media files | Uploaded content owned by an account |
| Playlists and schedules | Content composition and timing |
| Player inventory | The set of devices registered to an account |
| SMIL index | The generated playlist served to a player |

Uploaded media, rendered template items and generated SMIL indexes are stored
below `var/`, outside the web server's document root. They are never reachable
by a direct URL, only through the delivery scripts described in section 3.

---

## 3. Trust Boundaries

1. **Administrative interface** — authenticated, session-based, CSRF-protected.
   All account, media, playlist and player management happens here.
2. **Player endpoint (`GET /smil-index`)** — reachable without a session.
   Authentication is by possession of a randomly generated player UUID. See
   section 5.
3. **Browser media delivery (`media.php`)** — serves thumbnails and originals
   to the administrative interface. URLs are HMAC-signed with `APP_SECRET` and
   expire. The signature covers checksum, extension, variant and expiry, so a
   thumbnail URL cannot be edited into an original one.
4. **Player media delivery (`delivery.php`)** — serves the files referenced from
   a playlist to players. It deliberately runs without the application
   bootstrap (no container, session or database). Its current access check is
   limited, see section 8.

---

## 4. What garlic-hub Is Designed to Protect Against

- Unauthorised access to the administrative interface.
- Unauthorised modification of playlists, schedules, media or player assignments.
- Retrieval of an account's SMIL playlist by a party that does not possess the
  corresponding player UUID.
- Cross-account access through the administrative interface.
- Direct retrieval of stored files by URL: uploads and SMIL indexes are not in
  the document root.
- Use of administrative media URLs without a valid, unexpired signature, and
  tampering with the parameters of a signed URL.
- Common web application attack classes on authenticated routes: session
  fixation, CSRF, SQL injection, stored and reflected XSS, path traversal on
  upload and download handlers.

## 5. Player Authentication: Design Decision

**Behaviour.** A player identifies itself by a UUID transmitted in the
`User-Agent` header on every request to `/smil-index`. Where a device or an
intermediate proxy overrides the user agent string, the UUID may instead be sent
in `X-Signage-Agent`, which takes precedence when present. Possession of a valid
UUID is sufficient to retrieve the playlist associated with that player. The
endpoint is not behind session authentication.

**Rationale.** This is the established mechanism across the digital signage
industry, not only in SMIL-based systems. It follows directly from the
constraints in section 1: a device with no input capability, provisioned with
nothing but a URL, cannot present a separately issued credential.

**Security property.** Player UUIDs are randomly generated by the device at
installation time. They are not derived from MAC addresses, serial numbers or
any other enumerable value, and they are regenerated on firmware reset. This
holds for garlic-player and for the third-party devices garlic-hub is tested
against. The resulting search space is that of a random version 4 UUID and is not
practically enumerable.

A randomly generated, device-held, non-enumerable identifier presented on every
request is functionally equivalent to a bearer credential. The security property
provided is the same as that of a bearer token: possession grants access, and
disclosure is equivalent to credential disclosure.

**Accepted risk.** A party that obtains a player UUID through any channel can
retrieve that player's playlist. Operators must treat player UUIDs, and the
configured content URL, as credentials.

**Operator requirement.** Deploy over HTTPS. Over plaintext HTTP the UUID is
observable in transit, which defeats the mechanism entirely.

## 6. Player Self-Registration: Design Decision

**Behaviour.** A device contacting `/smil-index` with a previously unseen UUID
causes a player record to be created. The `owner_id` query parameter determines
which account the record is associated with.

**Rationale.** Field provisioning consists of entering a content URL on the
device. There is no mechanism in third-party signage firmware to transmit a
pairing code, provisioning token or any other proof of association. Requiring
such proof before record creation would make garlic-hub incompatible with the
hardware it exists to serve.

**Limitation of impact.** A newly created player record is inert. It receives no
playlist and no content. The endpoint serves nothing for that UUID unless and
until the account holder deliberately assigns a playlist to it through the
administrative interface. An account holder has no reason to assign content to a
device they do not recognise.

**Accepted risk.** A party that knows an installation's endpoint URL can cause
unused player records to appear in an account's inventory. The effect is limited
to unwanted rows in a list. Rate limiting is applied as a mitigation.

---

## 7. The `owner_id` Parameter

`owner_id` is an association parameter, not an access control parameter. Its only
function is to determine which account a newly created player record belongs to.
It has no role in the retrieval path.

Consequently, varying `owner_id` on requests for an existing player has no effect
on the response. This is expected behaviour. It does not constitute an
authorization bypass, because `owner_id` is not, and has never been, the value
that governs access. Access is governed by possession of the player UUID as
described in section 5.

---

## 8. Player Media Delivery: Current State and Known Limitation

**Behaviour.** Players fetch files from `delivery.php/<checksum>.<ext>` for
mediapool files and `delivery.php/tpl/<item_id>.<ext>` for rendered template
items. The script checks that the request carries a UUID-shaped value in the
`User-Agent` or `X-Signage-Agent` header, that the file name matches the
expected pattern for its source, that the extension is on a fixed list, and that
the resolved path stays inside the source directory.

**Known limitation.** The header check is a sanity filter, not access control.
It tests the shape of the value and does not verify the UUID against any
player. In addition, the checksum is the content hash of the file. It is used for
deduplication, is part of every exported playlist and appears in every URL log,
so it must not be treated as a secret. A party that knows a checksum, or the
numeric id of a template item, and sends any UUID-shaped header can retrieve that
file. Template item ids are small integers and therefore enumerable.

**Rationale.** The constraints of section 1 apply here as well: player firmware
cannot present a separately issued credential, and the script is kept free of
the application bootstrap so that the frequent revalidation requests of a large
player fleet stay cheap.

**Planned.** Links are to be signed per player and file with a non-expiring HMAC
over licence, checksum, extension and player UUID. The check stays free of
database access, so revoking a licence changes which links are placed in newly
generated playlists, but cannot invalidate a link that was already issued. This
is a deliberate trade-off against having to re-push playlists to the installed
base. Until then the limitation above is in effect.

**Accepted risk.** Media that is referenced by a playlist can be retrieved by
anyone who knows its checksum or item id. Operators should not upload content to
the mediapool that must stay confidential from third parties with knowledge of
the installation.

**Operator requirement.** Deploy over HTTPS, as for section 5.

## 9. Out of Scope

The following are outside the threat model. Reports in these categories will be
closed with a reference to this section.

- Behaviour described in sections 5, 6 and 7 as a design decision, absent a
  demonstrated attack that the stated security property does not already cover.
- Retrieval of a file from `delivery.php` with an arbitrary UUID-shaped header
  when its checksum or item id is known. This is the documented limitation in
  section 8 until signed player links are in place.
- Attacks that presuppose disclosure of a player UUID without demonstrating how
  that disclosure occurs.
- Attacks requiring plaintext HTTP deployment, contrary to section 5.
- Attacks requiring prior administrative access to the target account.
- Attacks requiring physical access to a player device.
- Denial of service through raw request volume.
- Vulnerabilities in third-party player firmware.
- Missing hardening headers, cookie flags or TLS configuration on a deployment,
  where these are the responsibility of the operator's reverse proxy.

---

## 10. In Scope

Reports demonstrating any of the following are in scope and will be treated as
security issues:

- Retrieval of an account's playlist or schedule data without possession of a
  corresponding player UUID.
- Retrieval of a file through `media.php` without a valid signature, or by
  altering a signed URL.
- Retrieval of a file through either delivery script that is not referenced by
  the documented checksum or item id schemes, and path traversal in either
  script.
- A practical method of obtaining or enumerating player UUIDs.
- Any cross-account access through the administrative interface.
- Authentication or session handling defects on administrative routes.
- Injection, traversal or deserialisation defects on any route.
- Privilege escalation between account roles.
- A registration flow satisfiable by standards-compliant signage firmware that
  would close the risk accepted in section 6. Such a report is welcome as a
  design contribution.

## 11. Reporting

See [SECURITY.md](https://github.com/garlic-signage/.github/blob/main/SECURITY.md) for the reporting process and GPG key.

Reports must include a proof of concept demonstrating the claimed impact. The
presence of a code pattern is not by itself a demonstration of impact. Where a
report claims cross-account access, the proof of concept must involve two
accounts and show data belonging to one being reached using means available to
the other.

Please agree on a severity assessment before requesting a CVE identifier or
contacting a CVE Numbering Authority.
